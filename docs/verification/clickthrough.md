# 클릭 통과 실측 기록

> 2026-09-14 / Windows 11 Pro 26200 / .NET SDK 9.0.318 / 1920x1080, 배율 100%

## 왜 쟀나

이 프로젝트 전체가 "펫이 없는 자리는 클릭이 그대로 통과한다"에 얹혀 있다.
안 되면 화면이 잠겨서 업무가 불가능하고, 그러면 설계를 통째로 바꿔야 한다.
말로 넘기지 않고 실제로 띄워서 쟀다.

## 무엇이 사실로 확인됐나

**WPF 투명 창은 클릭 통과를 코드 없이 처리한다.**

`AllowsTransparency="True"` 창은 픽셀 단위 알파값을 가진 합성 창이 된다.
완전히 투명한 픽셀은 윈도우가 "여기에 창이 없다"로 판정해 뒤 창으로 클릭을 넘긴다.
**사각형 영역 계산도, 마우스 감시도 필요 없다.** 그림이 그려진 모양 그대로 판정된다.

검사 시점에 `WS_EX_TRANSPARENT`(0x20)는 **꺼져 있었다**(ex-style `0x80088`).
그런데도 빈 공간 클릭이 뒤 창으로 갔다 — 이 비트와 무관하게 동작한다는 증거다.

## 측정 방법

각 지점에 커서를 놓고 `WindowFromPoint`로 **실제로 어느 창이 클릭을 받는지** 확인했다.
눈으로 본 게 아니라 OS에 물어본 값이다.

검사 스크립트: `scripts/verify-clickthrough.ps1`

## 결과

창 영역 `0,0 - 1920,1032`, ex-style `0x80088`

| 지점 | 좌표 | 기대 | 실제 | |
|---|---|---|---|---|
| 빈 화면 한가운데 | 960,516 | 통과 | 다른 창 | OK |
| 펫 왼쪽 빈 공간 | 660,976 | 통과 | 다른 창 | OK |
| 펫과 응아 사이 | 1090,1002 | 통과 | 다른 창 | OK |
| 펫 몸통 | 960,976 | 펫이 받음 | 펫 | OK |
| 응아 | 1184,1000 | 펫이 받음 | 펫 | OK |
| 상태판(반투명) | 60,40 | 펫이 받음 | 펫 | OK |

**6/6 통과.** 반투명(알파 0xCC) 영역도 정상적으로 클릭을 받는다.

## 성능

화면 전체를 덮는 투명 창은 무겁다는 통설이 있어 같이 쟀다.

| | 값 |
|---|---|
| CPU (5초 평균, 전체 코어 기준) | **0.23%** |
| 메모리 | 114 MB |

**문제 없다.** 화면 전체를 덮어도 비용이 사실상 0이다.
펫마다 창을 따로 띄우는 구조로 갈 이유가 없다.

## 이 측정으로 삭제된 코드

원래 커서 위치를 60ms마다 확인해 통과를 켰다 껐다 하는 장치(`ClickThroughController`)를 넣었었다.
측정 결과 불필요해서 **삭제했다.** 함께 사라진 것:

- 마우스 좌표를 읽는 `GetCursorPos` 호출 → 외부 함수 하나 감소
- 60ms 주기 타이머 → 상시 도는 루프 하나 감소

보안 검토 관점에서도 이득이다. 마우스를 전혀 읽지 않는 프로그램이 됐다.

## 함정 하나 (재현할 때 주의)

처음 검사에서 응아 지점이 실패했는데, 원인은 **펫이 아직 알이라 응아가 숨겨져 있던 것**이었다.
제품 결함이 아니라 검사 설정 문제였다.
부화한 상태의 세이브를 심고 다시 재서 통과를 확인했다.
