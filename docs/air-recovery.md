# Air의 PKP 로컬 복구 통로

상태(2026-11-05): 세 실행 파일 빌드·복구 핵심 단위 시험17개 통과. Air 앱과 독립 도우미를 설치했고, 실제 펫에서 운영체제 인증 성공 뒤 정상 준비 상태 확인·결과 저장·앱 교체/재기동 후 기록 유지까지 확인했다. 서버가 이미 실행 중인 경로였으며 서버를 끈 뒤 시작하는 실기 시험은 하지 않았다. 아래 명령은 실행·승인 범위를 함께 보존하는 절차이며 자동 반복 실행 지시가 아니다.

## 실제 확인과 반복 권한 요청 수정

- 실제 작업 `14588F8D-F92B-4CD6-AAD1-9A1DABBC9BF1`은 사용자 확인 대기 → 실행 중 → 준비 확인 완료로 기록됐다. SQLite 사건도 각 단계1행이다. 당시 ALFA PID90998·중계기 PID10756을 유지했고 강제 재시작하지 않았다.
- 16:37 확인에서 수정본 펫이 로컬 ALFA 준비와 같은 완료 기록을 표시했다. 확인 창을 닫았고 화면 도구도 종료 처리했다. 현재 운영체제 화면 공유 표시 자체의 종료 여부까지 이 기록으로 대신 증명하지 않는다.
- 기존 시작 경로는 보이지 않는 `ContentView`를 만들면서 게임패드·입력 변환기를 초기화했고, `InputSimulator.init()`이 Mac 제어 권한 요청을 자동 호출했다. 여러 임시 서명 빌드를 교체·재실행하면서 이 흐름을 반복한 것이 이번 수정 과정의 문제였다. 실제 시스템 권한을 초기화하거나 다시 허용하도록 요구하지 않았다.
- 현재 시작 경로는 펫·로컬 복구만 초기화한다. 스튜디오는 **스튜디오 열기**를 눌렀을 때 생성한다. 입력 변환기는 생성 시 권한 상태만 읽고, 권한 요청은 기존 스튜디오의 명시적인 권한 버튼에서만 한다. 권한이 없으면 가상 키·마우스 이벤트도 보내지 않는다. 복구에는 Mac 제어 권한이 필요하지 않다.
- 설치 후 복구 창을 한 번 안내하고, 앱을 다시 열면 복구 창을 연다. 자동 화면 촬영은 하지 않는다.
- 실제 설치에서 발견한 SQLite API 호환, Air의 `local-pg,wiki-git` 프로필·`currentSchema=alfa`, 임시 서명의 `# designated =>` 출력 형식을 수정했다. DB 대상과 코드 지문 검사는 유지한다. 이후 복구 핵심17개 시험이 통과했고, 마지막 시작 경로 수정은 앱 빌드와 실제 창의 상태/기록으로 확인했다. 게임 입력·음성 기능의 동작 회귀는 실행하지 않았다.
- 브라우저 기본 선택은 사용자 지정 Aside다. 이번 세션이 Chrome을 임의로 열었던 일을 시정해 Chrome의 인증 요청·앱과 앱 안 브라우저 임시 탭을 닫았다. 기본 브라우저 설정은 변경하지 않았고 `agent-desktop`을 실행하지 않았다.
- 공통 기기 인증은 서버200으로 정상 확인했다. 사용자 권한이 필요한 작업 도구의 인증은 별도 미연결이다. 이미 받은 로컬 빌드·시험·설치 승인을 유지하여 수행했고, 이를 공통 서버 승인 원장의 실행 영수증으로 위장하지 않았다.

미확인: 서버 중단 상태의 실제 시작, 다른 서명의 호출자 거절 실기, 운영체제 인증 취소 실기. 중복/취소/불확실 상태·재개/정책 변경은 가짜 서비스와 SQLite를 이용한 단위 시험으로 확인했다.

## 사용 흐름

설치 후 기존 메뉴바 펫의 **이 Mac의 ALFA 상태·복구**를 연다. **복구 계획 확인**에서 현재 선택된 서버와 접속 중계기를 확인한다. **사용자 확인 후 서버 시작**을 누르면 별도 복구 도우미가 macOS의 사용자 확인을 요구한다. 앱에서 보내는 `confirmed=true` 같은 값으로 대신할 수 없다.

이후 앱과 ALFA 서버가 꺼져도 도우미는 시작한 작업을 계속 처리한다. 앱을 다시 열면 저장된 작업 번호로 결과 조회를 재개한다. Intel, ALFA 로그인 서버, 모델, 인터넷 호출은 이 통로의 실행 조건이 아니다. Air가 잠들거나 로그아웃하면 이 사용자 서비스의 실행은 유지되지 않는다.

## 실제 대상과 제한

- `.alfa/router-target`이 `7711`이면 `com.alfa.backend.blue`, `7712`이면 `com.alfa.backend.green`을 선택한다.
- 여기에 `com.alfa.router`(7701)만 추가한다. 경로·명령·포트는 요청에서 입력받지 않는다.
- 등록되지 않은 서비스는 검증한 기존 LaunchAgent 파일로 `launchctl bootstrap`한다. 등록됐지만 멈춘 서비스는 `launchctl kickstart`한다. `-k`는 사용하지 않는다.
- 실행 중인 프로세스가 있으면 관찰만 한다. 불건강하더라도 종료·강제 재시작하지 않는다. 다른 프로세스가 포트를 점유하면 중단한다.
- 기존 설정의 네 가지 보조 서비스 자동 시작 값은 모두 `0`이어야 한다. 없거나 켜졌으면 설치를 거절한다. 두 DB 연결 주소는 PostgreSQL `127.0.0.1:15432/alfa_air_local`이어야 한다.
- PostgreSQL·Redis·Intel·원격 도메인·인증키·DB 복원·스키마 변경은 관리하지 않는다. 필요한 DB가 내려가 있으면 준비 성공으로 기록하지 않는다. 기존 ALFA 실행 파일 자체의 정상 시작 동작은 그대로다.

## 독립 실행·사용자 확인

`com.veloai.portkiller.recovery`라는 로그인 사용자 LaunchAgent가 `Contents/Helpers/PKPRecoveryHelper --serve`를 실행한다. 관리자 권한은 요구하지 않는다. macOS 13 이상의 앱 간 통신(NSXPC)을 사용하고 실제 사용자 번호와 설치된 실행 파일의 코드 서명 조건을 서로 확인한다. 현재 Air 앱은 개발자 인증서가 없는 임시 서명이므로 가상의 개발자 식별자는 사용하지 않는다. 이 방식은 같은 사용자의 악성 프로그램까지 격리하는 관리자 보안 경계는 아니다.

계획은 작업 번호, 설치 번호, 사용자 번호, 실행 정의의 지문, 선택된 서버, 90초 기한과 결합된다. 시스템 사용자 확인 뒤 다시 대조한다. 확인 창이 만료되거나 앱 연결이 끊어지면 확인 대기를 취소한다. 실행 접수 뒤에는 앱 연결 종료로 작업을 취소하거나 재실행하지 않는다.

## 기록·중복 처리

기록 위치는 `~/Library/Application Support/PortKillerRecovery/recovery.sqlite3`이다. 폴더는 사용자 전용 0700, 파일은 0600으로 만들고 링크와 다른 소유자를 거절한다. 이 파일은 ALFA 운영 DB와 별개다. 설치 정책도 같은 폴더의 `policy.json`에 보관한다.

계획 접수 → 사용자 확인 대기 → 실행 접수 → 성공/결과 확인 대기 순서로 작업과 사건을 트랜잭션에 기록한다. 계획에는 사용자·설치·대상이 연결된다. 같은 작업 번호의 재요청은 기존 결과를 돌려준다. 기록 DB의 유일성 제약과 프로세스 잠금이 실행 중이거나 결과가 불확실한 두 번째 복구를 차단한다.

도우미가 중간에 종료되면 `running`을 `unknown`으로 바꾸고 시작 명령을 반복하지 않는다. **사용자 확인 후 실제 결과 재확인**은 새 시스템 사용자 확인 뒤 프로세스·포트·로컬 상태 응답을 조회하고 성공 여부만 기록한다. 서버 명령을 실행하지 않는다. 여전히 준비되지 않았다면 수동 확인이 필요하며 새 복구를 무조건 허용하지 않는다. 자동으로 모호함을 없애려고 DB 행을 삭제하면 안 된다.

비밀·환경 변수·명령 원문 출력은 결과나 사건 기록에 저장하지 않는다. 명령 출력은 크기와 시간이 제한된 익명 임시 파일로만 처리하고 닫는다. 최근 20건을 화면에 표시하며 전체 작업 기록 상한은 5,000건이다. 상한 도달 시 새 접수를 거절한다. 이번 구현에는 자동 정리나 원격 기록 동기화가 없다.

## 설정 변경과 경쟁 조건

설치 시 앱·도우미·LaunchAgent·실행 스크립트·설정 파일의 존재 여부와 지문, 실제 서버 JAR와 Java·Node 실행 파일을 고정한다. 설정은 셸로 실행하지 않고 같은 지문의 파일 내용으로만 해석한다. 각 시작 명령 직전과 최종 성공 판정에서 다시 검사한다. 보조 서비스·설정·실행 파일이 바뀌면 기존 정책으로 복구하지 않는다. 업데이트는 새 정책 설치가 필요한 별도 작업이다.

대상 파일의 변경은 명령 직전·직후와 대기 중 대조한다. 기존 배포 프로그램과 공유하는 원자적 잠금은 아직 없다. 따라서 대조 직후 배포가 대상을 바꾸는 아주 짧은 경쟁 구간이 남으며, 이를 발견하면 결과 불확실로 남긴다. 운영 배포와 복구를 동시에 실행하지 않아야 한다. 같은 서비스의 두 프로세스를 직접 띄우지는 않고 서비스 관리자에 한 번 시작을 요청한다.

## 정확한 실행 묶음 — 승인 전 실행 금지

아래는 이번 소스에 대한 제안이며, 실행 성공 기록이 아니다. 실제 승인 계획은 ALFA의 `config/alfa/test-plans/pkp-air-recovery.json`에 코드 지문과 함께 고정한다. 개발 완료 후 승인받고 실행한다. 명령이나 소스가 바뀌면 이전 승인으로 재시도하지 않는다.

1. Air에서 로컬 SDK만 사용해 세 실행 파일을 빌드한다. 외부 패키지 설치·모델 호출·서비스 변경 없음. 최대 15분, 작업 병렬 수 2.

   ```sh
   /usr/bin/swift build --package-path /Users/aiso/Monster/github/PortKiller/Game -c release --jobs 2 --disable-automatic-resolution
   ```

2. 같은 설정으로 `RecoveryTests` 17개를 실행한다. 사용자 홈 아래 고유한 `.pkp-recovery-test-<UUID>` 폴더의 가짜 정책·SQLite·서비스만 사용하고 시험 뒤 제거한다. 실제 `launchctl`·인증 창·서버·DB는 호출하지 않는다. 최대 10분.

   ```sh
   /usr/bin/swift test --package-path /Users/aiso/Monster/github/PortKiller/Game -c release --jobs 2 --disable-automatic-resolution --filter RecoveryTests
   ```

3. 위 두 검사가 통과하고 설치가 승인된 경우에만 아래를 실행한다. 기존 캐릭터 자산을 복사하고 앱을 임시 서명한다. 이전 앱을 `~/Applications/PortKillerPet.before-recovery-<시각>.app`으로 보관한 뒤 복구 도우미만 등록한다. 기존 실행 중인 펫은 이 명령으로 종료하지 않는다.

   ```sh
   /bin/bash /Users/aiso/Monster/github/PortKiller/Game/Tools/package-air.sh
   ```

4. 설치 후 기존 메뉴바 펫 하나만 승인받아 재기동한다. 이 단계의 `-k`는 **펫 앱**에만 적용한다. ALFA 서버에 적용하지 않는다.

   ```sh
   /bin/launchctl kickstart -k gui/$(id -u)/com.veloai.portkiller.pet
   ```

5. 복구 창에서 계획·취소·상태·기록을 확인한다. 시스템 사용자 확인은 사용자가 직접 수행한다. 정상 실행 중인 서버에서 실행하면 서버 프로세스가 바뀌지 않아야 한다. 앱 재개 후 기존 작업 조회가 이어져야 한다. 허용되지 않은 앱 거절·인증 만료·연결 끊김·불확실 작업의 재확인도 별도 실기 검증 대상이다.

6. 서버를 실제로 끈 복구 시험은 별도 승인 범위다. 현재 Air ALFA를 임의로 중단하지 않는다. 이 시험이 끝나기 전에는 “ALFA가 내려간 상황에서 실제 복구 성공”을 주장하지 않는다. Intel을 원격으로 끄거나 접속할 필요는 없다.

공통 승인 도구의 사용자 연결과 서버 기록은 미연결이다. 사용자는 로컬 빌드·시험·앱/도우미 설치·펫 재기동 범위를 명시 승인했고 이후 같은 승인을 재질문하지 말고 진행하도록 지시했다. 현재 작업 계약의 관리 도구 인증 부재와 이미 승인된 격리 작업의 분리 원칙에 따라 위 로컬 작업을 수행했다. 새 인증키·사용자 권한·가짜 서버 승인 기록은 만들지 않았다.

## 제거와 불완전 설치

승인된 제거 시 설치 앱의 `Contents/Helpers/PKPRecoverySetup uninstall`을 사용한다. 디스크 파일과 실제 등록된 도우미 실행 정의가 같아야 도우미만 해제한다. 정책은 보관 이름으로 옮기고 기록 DB·원래 펫 자동 실행·ALFA 서비스는 유지한다. 진행 중 복구를 강제 제거하지 않도록 먼저 해당 작업 결과를 확인해야 한다.

설치 결과가 불확실하면 정책과 기록을 지우거나 반복 설치하지 않는다. 이전 앱 백업과 새 앱, 도우미 등록 상태를 함께 검토한다. 앱 교체 자체가 실패해 원래 위치가 비어 있으면 포장 스크립트가 기존 앱을 복원한다. 도우미 등록이 일부 진행된 경우에는 이를 숨기고 이전 앱으로 자동 복귀하지 않는다.
